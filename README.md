# Safe Backup Manager

WordPress 管理画面からバックアップの作成・一覧表示・ダウンロード・削除を行うプラグイン（試作版 v0.1.0）。

wp-content ディレクトリとデータベースを **1つの ZIP** にまとめ、Web から直接アクセスできない場所に保存します。

## 機能

| 要件 | 実装 |
| --- | --- |
| 独自の管理ページ | 「ツール > バックアップ」（`add_management_page`） |
| 「バックアップを作成」ボタン | POST フォーム → `admin-post.php`（nonce 付き）。押下後はボタンを無効化し二重送信を防止 |
| 履歴表示 | 作成日時・ファイル名・ファイルサイズ・内容（ファイル数／テーブル数）・操作（ダウンロード／削除）。SHA-256 も表示 |
| ダウンロード | バックアップ **ID** を指定し、権限と nonce を確認したうえで PHP からストリーミング送信 |
| ZIP 形式・構造維持 | `wp-content/...` をそのままのパスで格納。`database/database.sql`・`sbm-manifest.json` を同梱 |
| サーバーへ保存 | 既定は **WordPress 設置ディレクトリの1つ上**（ドキュメントルート外）。書き込めない場合のみ uploads 配下 |
| エラー処理 | 対象ディレクトリなし／保存先作成・書き込み失敗／ZIP 作成失敗／空き容量不足／実行中の二重起動／存在しないバックアップ／ファイル消失 を、それぞれ具体的なメッセージで表示 |
| （追加）削除 | 確認ダイアログ付き。保持世代管理の前提になるため実装 |
| （追加）作成後の検証 | ZIP を開き直して整合性（`CHECKCONS`）とエントリ数を確認してから確定 |

### ZIP の中身

```
backup-20261109-162553-55262382f459.zip
├── wp-content/            … wp-content のディレクトリ構造をそのまま保持
│   ├── plugins/
│   ├── themes/
│   └── uploads/
├── database/database.sql  … このサイト（$table_prefix）のテーブルの構造とデータ
└── sbm-manifest.json      … 作成日時・WP/PHP バージョン・テーブル一覧・スキップしたファイル等
```

除外するもの: このプラグインの保存先、`wp-content/cache`、`wp-content/upgrade`、`wp-content/upgrade-temp-backup`、シンボリックリンク（フィルター `sbm_backup_excluded_paths` で変更可）。

## 動作環境・インストール

- WordPress 6.4 以上（`wp_admin_notice()` を使用）
- PHP 7.4 以上、**zip 拡張（ZipArchive）**、mysqli
- 確認環境: Local 10.2 / WordPress 7.1.4 / PHP 8.2.29 / MySQL 8.4.0 / **nginx** 1.26.1 / Windows 11

1. このリポジトリを `wp-content/plugins/safe-backup-manager/` に配置する
2. 管理画面「プラグイン」で有効化する
3. 「ツール > バックアップ」を開く

### 保存先を指定する場合（推奨）

`wp-config.php` で絶対パスを指定できます。ドキュメントルート外のディレクトリを指定してください。

```php
define( 'SBM_BACKUP_DIR', '/home/example/backups/example.com' );
```

### uploads 配下に保存される場合の nginx 設定

設置ディレクトリの1つ上に書き込めないサーバーでは uploads 配下に保存されます。Apache / IIS は自動で配置する `.htaccess` / `web.config` でアクセスを拒否しますが、**nginx はこれらを読まない**ため、管理画面に警告を表示します。その場合はサーバー設定で拒否してください。

```nginx
location ~ /sbm-backups-[A-Za-z0-9]+/ { deny all; }
```

## ファイル構成

```
safe-backup-manager/
├── safe-backup-manager.php                 … 起動処理（定数定義・読み込み・管理画面でのみフック登録）
├── uninstall.php                           … 削除時に設定・履歴のオプションを削除（ZIP は残す）
├── includes/
│   ├── class-sbm-admin.php                 … 管理画面の表示と作成・ダウンロード・削除リクエストの処理
│   ├── class-sbm-backup-creator.php        … 対象ファイル列挙・ZIP 作成・検証・ロック
│   ├── class-sbm-database-exporter.php     … $wpdb による SQL ダンプ
│   ├── class-sbm-backup-repository.php     … 履歴の保存（wp_options）
│   ├── class-sbm-storage.php               … 保存先の決定・作成・保護ファイル
│   └── class-sbm-exception.php             … 画面に表示してよいエラー
└── tests/
    └── smoke-test.php                      … WP-CLI で実行する動作確認スクリプト
```

責務ごとにクラスを分け、依存はコンストラクタで渡しています（テストで保存先を差し替えられるようにするため。実際に T3 で利用）。将来「外部ストレージに送る」「スケジュール実行する」処理を追加するときも、`SBM_Backup_Creator::create()` を呼ぶだけで済む構成です。

## ① 要件分析

### 実案件で事前に確認すべき事項

| 分類 | 確認事項 | 理由 |
| --- | --- | --- |
| 目的 | **復旧目標（RPO / RTO）**。何時間前の状態まで戻せればよいか、何時間以内に復旧したいか | 取得頻度・方式・保存先がこれで決まる |
| 目的 | 既存のレンタルサーバーのバックアップとの役割分担（保持期間・復元方法・費用） | 二重投資や、どちらにも無い「穴」を避ける |
| 対象 | バックアップ範囲（DB／アップロード画像／テーマ・プラグイン／WP 本体／wp-config.php／.htaccess） | wp-config.php は DB パスワードを含み、漏えい時の影響が大きい |
| 対象 | サイト規模（ファイル容量・ファイル数・DB サイズ）と今後の増加見込み | 1リクエストで処理できるか、の判断材料 |
| 対象 | 個人情報の有無（問い合わせ・会員・EC 注文）と社内の取り扱い規程 | バックアップ自体が漏えい対象になる。暗号化・保管場所・保管期間の要件が変わる |
| 環境 | サーバーの種類（共用／VPS）、Web サーバー（Apache / nginx）、PHP バージョン、zip 拡張、`exec()` 可否 | 実装方式と直接アクセス対策の方法が変わる |
| 環境 | ディスク容量・PHP の実行時間制限・メモリ制限・FastCGI のタイムアウト | ZIP はサイトと同程度の空き容量を使う |
| 環境 | マルチサイトか、同じ DB に別サイトのテーブルが同居していないか | ダンプ対象の範囲 |
| 運用 | 操作できる人（管理者のみか、制作会社の担当者もか） | 権限設計 |
| 運用 | ダウンロードしたファイルの保管ルール（誰の PC に、どれだけの期間） | 漏えいの経路は「サーバー」より「ダウンロード後」の方が多い |
| 運用 | 保持世代数・保持期間、保存先の容量上限 | 自動削除の仕様 |
| 運用 | 実行時間帯の制約（アクセスの少ない時間帯）、失敗時の通知先 | サイトの安定性・気付けるかどうか |
| 運用 | 復旧作業を誰が行うか（クライアント自身か当社か）、復旧手順書の要否 | 「復旧できる状態」の定義 |

### 今回置いた前提条件

| 未確認事項 | 今回の前提 |
| --- | --- |
| 対象範囲 | **wp-content 全体 ＋ このサイトのテーブル**。WP 本体は公式から再取得できるため対象外（バージョンはマニフェストに記録）。**wp-config.php は秘密情報を含むため対象外**（復旧時に新しく作成する） |
| サイト規模 | 中小規模（数 GB 程度まで）。1 回の HTTP リクエスト内で同期処理する |
| サーバー | 共用レンタルサーバーを想定し、`exec()`・外部コマンドに依存しない。zip 拡張は有効とし、無ければエラー表示 |
| Web サーバー | Apache / nginx の両方を想定（ローカルは nginx） |
| 操作者 | `manage_options` 権限（管理者）のみ |
| 保存先 | 同一サーバー内。ドキュメントルート外を優先 |
| 保持世代 | 自動削除なし（手動削除を用意） |
| 暗号化 | 今回はなし（保存場所と権限で保護）。今後の課題とする |
| マルチサイト | 対象外（未検証） |
| 一貫性 | 管理者が任意のタイミングで実行。実行中の更新（注文・投稿）との厳密な整合性は保証しない |

## ② 技術選定

### 実装方式の比較

| 項目 | 採用 | 検討した代替案 | 判断理由 |
| --- | --- | --- | --- |
| ZIP 作成 | **ZipArchive**（PHP の zip 拡張） | PclZip（WP 同梱） | PclZip は純 PHP で遅く、メモリ消費も大きい。ZipArchive は C 実装で、`addFile()` は close 時にディスクから順次読むためメモリを圧迫しにくい。多くのレンタルサーバーで有効 |
| | | `exec('zip')` / `tar` | 高速だが共用サーバーでは `exec()` が無効なことが多く、引数組み立てのコマンドインジェクション対策も必要 |
| | | ZipStream-PHP（外部ライブラリ） | 「保存せずにそのままダウンロード」には最適だが、今回は「サーバーに保存」が要件 |
| DB ダンプ | **$wpdb で SELECT → SQL ファイル** | `mysqldump` コマンド | 最も確実で高速だが `exec()` 依存。将来、使える環境では優先的に使う設計が望ましい |
| | | mysqldump-php（外部ライブラリ） | PDO 前提で、WP の接続設定（ソケット・SSL 等）と二重管理になる。今回の規模では自前実装で足り、依存も増やさない |
| 実行方式 | **admin-post.php で同期実行** | Ajax ＋ 分割実行 | 大規模サイトに強く進捗表示もできるが、状態管理（どこまで処理したか）が複雑になり試作の範囲を超える。⑤で検討 |
| | | WP-Cron でバックグラウンド実行 | 画面が待たされないが、アクセスがないと動かない・失敗に気付きにくい。⑤の自動化で利用 |
| 履歴の保存 | **wp_options（autoload 無効）** | 専用テーブル | 件数は数十件程度でテーブル追加・マイグレーションの手間に見合わない |
| | | ディレクトリを都度スキャン | 作成者・SHA-256・ファイル数などのメタ情報を持てない |
| ファイル操作 | **PHP の標準関数** | WP_Filesystem API | WP_Filesystem は FTP 経由の書き込みにも対応するための抽象化だが、ZipArchive・ストリーム送信はローカルパスが必須のため使えない。代わりに `wp_mkdir_p()`・`wp_is_writable()`・`wp_delete_file()` 等の WP 関数を使用 |
| 外部ライブラリ | **なし** | — | 必要な機能が標準 API で実現でき、Composer 依存（vendor 同梱・脆弱性追従）を増やさない方が保守しやすいと判断 |

### 使用した WordPress API

| 用途 | API |
| --- | --- |
| 管理メニュー | `add_management_page()`、`admin_menu` |
| フォーム処理 | `admin_post_{action}`、`wp_safe_redirect()`（PRG パターン） |
| 権限・CSRF | `current_user_can()`、`wp_nonce_field()`、`wp_nonce_url()`、`check_admin_referer()` |
| 通知 | `wp_admin_notice()`、Transients API（`set_transient()` 等。メッセージを URL に載せないため） |
| DB | `$wpdb->get_results()`、`$wpdb->prepare()`、`$wpdb->esc_like()` |
| 設定・履歴・ロック | Options API（`add_option()` が既存時に false を返す性質を排他制御に利用） |
| ファイル | `wp_upload_dir()`、`wp_mkdir_p()`、`wp_is_writable()`、`wp_delete_file()`、`wp_normalize_path()` |
| 出力 | `esc_html()`、`esc_attr()`、`esc_url()`、`esc_js()`、`size_format()`、`wp_date()`、`number_format_i18n()` |
| その他 | `wp_raise_memory_limit()`、`nocache_headers()`、`apply_filters()`（対象・除外の拡張点）、`register_activation_hook()`、`uninstall.php` |

### コーディング規約

WordPress Coding Standards（インデントはタブ、Yoda 条件、`array()` 記法、エスケープ・nonce・権限チェック）を意識して記述しています。規約上あえて外している箇所には理由を付けて `phpcs:ignore` を記載しています（例: ZipArchive のためにローカルファイル関数を直接使う）。

UI 文字列は社内利用を前提に日本語で直接記述し、`__()` 等で囲んでいます（英語原文＋翻訳ファイルという WP 公式の流儀には沿っていません。配布する場合は英語原文化と `.po/.mo` 作成が必要）。

## ③ バックアップと復旧

### バックアップできる範囲

| 対象 | 含む | 備考 |
| --- | --- | --- |
| データベース | ○ | `$table_prefix` で始まる全テーブル（構造＋データ） |
| メディア（uploads） | ○ | |
| テーマ・プラグイン | ○ | 有料プラグインのライセンス情報が DB にある場合も DB 側で復元される |
| WordPress 本体 | × | 公式から同じバージョンを取得（マニフェストにバージョンを記録） |
| wp-config.php | × | DB パスワード・認証キーを含むため意図的に除外 |
| ルートの .htaccess、wp-content 外のファイル | × | 独自に置いたファイルがある場合はフィルター `sbm_backup_sources` で追加可能 |
| キャッシュ・更新用一時ディレクトリ | × | 再生成できるため |

### 復旧に必要な条件と手順

**必要な条件**

1. バックアップ ZIP が**サーバーの外にも**保管されていること（サーバー自体の障害・乗っ取りに備える。現状は手動ダウンロード）
2. 同じ（またはより新しい）バージョンの WordPress 本体と、要件を満たす PHP / MySQL 環境
3. 新しい DB の接続情報（wp-config.php は再作成）
4. SQL をインポートする手段（phpMyAdmin・`mysql` コマンド。大きい場合はコマンド推奨）
5. ドメインが変わる場合は URL 置換手段（WP-CLI `wp search-replace`。シリアライズされたデータを壊さないため SQL の単純置換は不可）

**手順**

1. 新環境に `sbm-manifest.json` の `wp_version` と同じ WordPress 本体を配置
2. 空の DB を作成し、`database/database.sql` をインポート
   `mysql -u USER -p --default-character-set=utf8mb4 DBNAME < database/database.sql`
3. `wp-config.php` を作成（DB 接続情報と、マニフェストの `table_prefix` を設定）
4. 既存の `wp-content` を ZIP 内の `wp-content` で置き換える
5. ドメインが異なる場合は `wp search-replace 'https://旧' 'https://新'`
6. 管理画面にログインし、パーマリンク設定を保存（リライトルール再生成）、表示・フォーム等を確認

### バックアップが正常に取得できたことの検証方法

| 段階 | 方法 | 実装状況 |
| --- | --- | --- |
| 作成直後（自動） | ZIP を `ZipArchive::CHECKCONS` で開き直し、エントリ数が想定（ファイル数＋SQL＋マニフェスト）と一致し SQL が含まれることを確認。失敗したら履歴に登録せず削除 | ○ |
| 作成直後（自動） | 一時ファイル名（`.part`）で作成し、検証後にリネーム。途中で失敗した ZIP が「成功」として残らない | ○ |
| 改ざん・転送破損の検知 | 作成時の SHA-256 を履歴に保存・表示。ダウンロード後に `sha256sum` / `Get-FileHash` で照合できる | ○ |
| 内容の確認 | 読めずにスキップしたファイル数を履歴と通知に表示（一覧はマニフェストに記録） | ○ |
| 復元できることの確認 | 別 DB に SQL をインポートし、テーブルごとの行数・内容を元 DB と比較 | 手動で実施（下記テスト結果 R1） |
| 定期的な確認（運用） | 月1回程度、ステージング環境で実際に復元するリハーサル | 運用提案 |

## ④ セキュリティ対策

課題では任意とされていますが、「不正アクセスによるバックアップデータの漏えいを防ぎたい」という要望の中心に関わるため、以下を実装しました。バックアップには**ユーザー情報（パスワードハッシュ・メールアドレス）を含む DB 全体**が入っているので、サイト本体と同等以上に守るべきデータとして扱っています。

| 脅威 | 対策 |
| --- | --- |
| URL を推測されて直接ダウンロードされる | 既定の保存先を**ドキュメントルート外**にした。uploads 配下に保存せざるを得ない場合も、ディレクトリ名（ランダム20文字）とファイル名（ランダム12桁）を推測困難にし、`.htaccess` / `web.config` / `index.php` を配置。nginx の場合は警告を表示 |
| 権限のないユーザーによる操作 | すべての画面・処理で `manage_options` を確認 |
| CSRF（管理者に意図しない作成・削除をさせる） | 作成・削除は POST ＋ nonce。ダウンロード・削除の nonce は**バックアップごと**に発行 |
| パストラバーサル（`../../wp-config.php` 等の取得） | ダウンロードはファイル名ではなく**履歴の ID**（16進32桁）で指定し、登録済みのファイルだけを返す。保存先のパス生成でも `..`・区切り文字を拒否 |
| エラーメッセージからの情報漏えい | 想定外の例外は画面に汎用メッセージのみ、詳細は `error_log` へ |
| 通知メッセージの偽装 | メッセージを URL パラメータで渡さず、ユーザーごとの transient に保存 |
| 復元後に「実行中」状態が残る | 実行中ロックと通知の一時データを SQL ダンプから除外（テスト中に発見した不具合の修正） |
| シンボリックリンク経由でサイト外のファイルが混入 | シンボリックリンクはたどらない |

**実装していない対策（今後の課題）**

- ZIP の暗号化（保存時・外部送信時）。漏えい時の被害を抑える最も効果の大きい対策
- ダウンロード前の再認証（パスワード再入力や2要素認証）と、ダウンロード操作の監査ログ
- ダウンロード URL の有効期限（現状は nonce の有効期限＝最大24時間に依存）

## ⑤ 今後の機能拡張

### 1日1回の自動バックアップ

- **スケジュール**: WP-Cron（`wp_schedule_event( ..., 'daily', 'sbm_daily_backup' )`）で登録。ただし WP-Cron はアクセスがあったときに動く仕組みのため、アクセスの少ないサイトでは時刻がずれる・重い処理が訪問者のリクエストに乗る、という問題がある。本番では `DISABLE_WP_CRON` を有効にし、**サーバーの cron から WP-CLI（`wp cron event run --due-now`）または独自コマンド `wp sbm backup` を実行**する構成を推奨
- **実行時間帯**: アクセスの少ない深夜帯。複数サイトを同じサーバーで運用する場合は時刻をずらす
- **失敗の検知**: 失敗時に管理者へメール（`wp_mail()`）。加えて「最後に成功したのが 26 時間以上前なら通知」という**成功の監視**も入れる（失敗処理自体が動かないケースに備える）
- 既存の `SBM_Backup_Creator::create()` とロックをそのまま流用できる

### Google Drive 等の外部ストレージへの保存

- **目的**: サーバー自体の障害・乗っ取り時にもバックアップを残すこと。同一サーバー内のバックアップは攻撃者に一緒に削除されうる
- **保存先の候補**
  - Google Drive: Google Drive API（OAuth 2.0）。共有ドライブに保存し個人アカウントに依存しない。5 MB 超は resumable upload
  - S3 互換ストレージ（Amazon S3 / Cloudflare R2 / Wasabi 等）: マルチパートアップロード、ライフサイクルルールによる自動削除、**オブジェクトロック（一定期間削除・上書き不可）**が使え、改ざん・ランサムウェア対策として優れる。業務用途ではこちらを第一候補に提案したい
- **構成**: `SBM_Destination` インターフェース（`upload()` / `list()` / `delete()`）を定義し、ローカル・Google Drive・S3 を実装として差し替えられるようにする。SDK は Composer で導入し、名前空間の衝突を避けるため Strauss 等でプレフィックスを付けて同梱
- **認証情報の保管**: アクセスキーは DB ではなく `wp-config.php` の定数か環境変数に置く。書き込み専用（削除権限なし）のキーにすると、サイトが乗っ取られても過去のバックアップを消されない
- **暗号化**: 送信前に libsodium（`sodium_crypto_secretstream_*`）でストリーム暗号化し、鍵はサーバー外でも保管
- **処理**: アップロードは時間がかかるため、作成とは別の非同期ジョブ（Action Scheduler 等）で行い、リトライ・失敗通知を付ける

### 過去30日分のバックアップ管理

- 作成成功後に、`created_at` が 30 日より古いものを削除する保持ポリシーを実行（**新しいバックアップの成功を確認してから**古いものを消す）
- 設定値（保持日数・最大世代数）を設定画面で変更可能にする。容量上限による削除も併用
- 外部ストレージ側は、プラグインからの削除ではなく**ストレージのライフサイクルルール**で消す（書き込み専用キーと組み合わせるため）
- 長期保存が必要なら GFS 方式（日次30世代＋週次＋月次）を提案
- ディスク容量の見積もり: 1回のサイズ × 30 世代 ＋ 作成時の一時領域。共用サーバーでは足りないことが多いため、**ローカル保持は数世代、30日分は外部ストレージ**という分担が現実的

### 大容量サイト（例: 50GB）への対応

今回の「1リクエストで全ファイルを ZIP にまとめる」方式は、50GB では成り立ちません（実行時間制限・FastCGI タイムアウト、作成中に 50GB 前後の空き容量が必要、CPU 負荷によるサイトの不安定化）。

- **分割実行**: 「ファイル列挙 → N 件ずつ追加 → DB をテーブルごと・行範囲ごと」をジョブに分け、Action Scheduler（WooCommerce 等で実績のあるキューライブラリ）で順に実行。状態を保存し、途中で止まっても再開できるようにする
- **差分（増分）バックアップ**: ファイルごとのパス・サイズ・更新日時（必要ならハッシュ）を前回分と比較し、変更分だけを保存。50GB の大半は変更のない画像なので効果が大きい
- **アーカイブの分割**: 1ファイル数 GB ごとに分け、アップロード・ダウンロードの失敗時に部分的にやり直せるようにする
- **DB**: 使える環境では `mysqldump --single-transaction --quick`（InnoDB で一貫性のあるスナップショット、行を逐次出力）。今回の LIMIT/OFFSET 方式は大きなテーブルでは後半ほど遅くなるため、主キー範囲で区切る方式に変える
- **構成の見直し**: そもそも PHP で処理するより、サーバーレベルのツール（rsync・restic・borg、VPS ならスナップショット）の方が適している。メディアを S3 等に置く構成（オフロード）にすれば WP サーバー側のバックアップ対象自体が小さくなる。この規模ではプラグインは「実行の指示と結果の表示」に徹し、重い処理はサーバー側に任せる構成を提案したい
- **負荷対策**: 深夜帯に実行、`nice`/`ionice` で優先度を下げる、画像など圧縮効果のないファイルは無圧縮で格納（今回も実装済み）

## 未実装事項と今後の改善方針

| 項目 | 理由 | 対応方針 |
| --- | --- | --- |
| 復元機能（管理画面から） | 復元は失敗するとサイトが動かなくなる高リスク操作で、試作の時間内で安全に作れないため。手順は③に記載 | まずは復元手順書と WP-CLI コマンドで対応。画面からの復元は、復元前の自動バックアップ・メンテナンスモード・ロールバックとセットで設計する |
| 大規模サイト対応（分割・非同期実行） | 状態管理が複雑になり試作の範囲を超えるため | ⑤の通り Action Scheduler による分割実行と差分バックアップ |
| 自動バックアップ・外部保存・保持世代 | 必須範囲外 | ⑤の通り。作成処理は `create()` に集約済みのため追加しやすい |
| ZIP の暗号化 | 鍵管理（どこに置くか・紛失時どうするか）をクライアントと決める必要があるため | libsodium によるストリーム暗号化。鍵はサーバー外に保管 |
| DB ダンプの一貫性 | 試作では対応を見送った。InnoDB なら `START TRANSACTION WITH CONSISTENT SNAPSHOT` で改善できるが、ロック・接続の扱いの検証が必要 | 一貫性のあるスナップショット取得、または `mysqldump --single-transaction` が使える環境では優先 |
| 進捗表示 | 同期実行のため | 非同期化と合わせて Ajax でポーリング |
| ダウンロードの監査ログ・再認証 | 時間の都合 | 誰がいつダウンロードしたかを記録。ダウンロード前にパスワード再入力 |
| 翻訳対応 | 社内利用前提のため日本語で直接記述 | 配布する場合は英語原文化と翻訳ファイルの作成 |
| PHPCS・PHPUnit | 時間の都合で WP-CLI のスモークテストのみ | Composer で WPCS・PHPUnit（wp-env）を導入し、GitHub Actions で自動実行 |
