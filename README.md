# Safe Backup Manager

WordPressの管理画面から、サイトのバックアップを作成・一覧表示・ダウンロードできるプラグインです（制作版 v0.1.0）。

「バックアップを作成」ボタンを押すと、サイトのファイルとデータベースを1つのZIPファイルにまとめて、サーバーに保存します。

## 導入方法

1. ZIPを展開し、`safe-backup-manager` フォルダを `wp-content/plugins/` に置く
2. 管理画面の「プラグイン」で「Safe Backup Manager」を有効化する
3. 「ツール」→「バックアップ」を開く

※ WordPress 6.4以上、PHP 7.4以上（zip拡張が有効なこと）で動作します。

## ① 要件分析

### 実案件なら事前に確認したいこと

クライアントの要望は「バックアップを取りたい」「漏えいを防ぎたい」「復旧できるようにしたい」というものですが、実際に作る前には、次のようなことを確認する必要があると考えました。

**何のために、どこまで戻せればよいか**

- 障害が起きたとき、「何時間前の状態」まで戻せればよいか（毎日取るのか、更新のたびに取るのか、で作りが変わります）
- 復旧にどれくらいの時間をかけてよいか
- 今使っているレンタルサーバーのバックアップと、どう役割を分けるか（同じことを二重にやっても意味がないため）

**何をバックアップするか**

- データベース、画像、テーマ、プラグイン、WordPress本体、設定ファイル（wp-config.php）のどれが必要か
- サイトの容量はどれくらいか、今後どれくらい増えそうか
- お問い合わせフォームの内容や会員情報、注文情報などの個人情報が含まれるか（含まれる場合、バックアップ自体を厳重に扱う必要があります）

**サーバーの環境**

- どのレンタルサーバーか、Webサーバーの種類（Apacheかnginxか）、PHPのバージョン
- サーバーの空き容量（ZIPを作るにはサイトと同じくらいの空きが必要です）
- 1回の処理にかけられる時間の上限

**運用**

- 誰がバックアップを操作するか（管理者だけか、制作会社の担当者もか）
- ダウンロードしたファイルを誰がどこに保管するか（サーバーよりも、ダウンロードした後のPCから漏れることの方が多いため）
- 何世代（何日分）残すか
- 復旧作業は誰が行うか（クライアント自身か、当社か）

### 今回置いた前提条件

上記は今回確認できないため、次のように決めて作りました。

- バックアップするのは wp-content とデータベース（wp-config.php はパスワードを含むので除外）
- 対象は数GB程度までのサイトで、一般的なレンタルサーバーで動かす
- 操作できるのは管理者だけで、保存先は同じサーバーの中

## ② 技術選定

### ZIPファイルの作り方

ZIPファイルを作る機能では、PHPに用意されている「ZipArchive」を採用しました。ZIPを作る方法には、ほかに「PclZip」と「サーバーのzipコマンドを直接実行する方法」がありますが、ZipArchiveはPclZipより処理が速くメモリも少なくて済み、zipコマンドと違って多くのレンタルサーバーで使えるため、この3つの中で一番バランスがよいと判断しました。

- PclZipは、WordPressに最初から入っているので、どのサーバーでも使えるのが良い点です。ただ、処理が遅く、メモリを多く使うため、大きなサイトでは途中で止まりやすくなります。
- zipコマンドは、3つの中で一番速いのが良い点です。ただ、PHPからサーバーのコマンドを実行する機能は、多くのレンタルサーバーで禁止されています。
- ZipArchiveの弱点は、サーバーで「zip拡張」が無効になっていると使えないことです。その場合は、理由が分かるエラーメッセージを表示するようにしました。

### データベースの書き出し方

データベースの中身をファイルに書き出す機能では、WordPressに用意されているデータベース操作の仕組み「$wpdb」を使い、データを少しずつ読み出して書き出す方法を採用しました。ほかに「mysqldumpコマンド」と「外部ライブラリ（mysqldump-php）」がありますが、$wpdbはmysqldumpコマンドと違ってどのサーバーでも動き、外部ライブラリと違ってWordPressの接続設定をそのまま使えるため、この方法にしました。

- mysqldumpコマンドは、速くて確実なのが良い点です。ただ、zipコマンドと同じく、レンタルサーバーでは使えないことが多いです。
- 外部ライブラリは、機能が豊富なのが良い点です。ただ、WordPressとは別にデータベースへ接続する設定が必要になり、管理するものが増えます。
- $wpdbの弱点は、大きなデータベースでは時間がかかることです。一度に全部を読み込まないようにしているので、メモリ不足にはなりにくくしています。

### 処理の実行方法

バックアップを実行する機能では、ボタンを押したらその場で最後まで処理する方法を採用しました。ほかに「少しずつ分けて処理する方法」がありますが、その場で処理する方法は仕組みがシンプルで結果もすぐ分かるため、制作には向いていると判断しました。

- 少しずつ分けて処理する方法は、大きなサイトでも時間切れにならず、進み具合も表示できるのが良い点です。ただ、「どこまで終わったか」を記録して続きから再開する仕組みが必要になり、今回の制作の範囲を超えるため見送りました。
- その場で処理する方法の弱点は、大きなサイトだと時間切れになることです。大きなサイトへの対応は、⑤に書いています。

### 外部ライブラリ

使っていません。必要な機能がPHPとWordPressの標準機能だけで作れたためです。外部ライブラリを使うと、そのライブラリの更新や脆弱性への対応もこちらでやらなければならず、保守の手間が増えます。

### 使ったWordPressの機能（API）

- 管理画面にページを追加：`add_management_page()`
- ボタンを押したときの処理を受け付ける：`admin_post_〇〇`（WordPress標準のフォーム送信の受け口）
- 操作した人が管理者か確認：`current_user_can()`
- 本人が画面から操作したものか確認：`wp_nonce_field()`、`check_admin_referer()`（「nonce」という、1回ごとの合言葉のようなものを使って、外部サイトからなりすまして操作されるのを防ぎます）
- 処理結果のメッセージ表示：`wp_admin_notice()`、`set_transient()`
- バックアップ履歴の保存：`get_option()`、`update_option()`
- データベースの読み出し：`$wpdb`、`$wpdb->prepare()`
- フォルダの作成・ファイルの削除：`wp_mkdir_p()`、`wp_delete_file()`
- 画面に表示する文字を安全にする：`esc_html()`、`esc_url()` など
- 日時やファイルサイズを見やすく表示：`wp_date()`、`size_format()`

## ③ バックアップと復旧

### バックアップできる範囲

**含まれるもの**

- データベース（投稿、固定ページ、コメント、設定、ユーザーなど）
- アップロードした画像やファイル
- テーマ
- プラグイン

**含まれないもの**

- WordPress本体（公式サイトから同じバージョンをダウンロードできるため）
- wp-config.php（データベースのパスワードが入っているため。復旧時に新しく作ります）
- キャッシュなどの一時ファイル（なくても自動で作り直されるため）

### 復旧するために必要な条件

1. **バックアップのZIPがサーバーの外にもあること**
   サーバーが壊れたり乗っ取られたりすると、サーバーの中のバックアップも一緒に失われる可能性があります。今回の制作では、作成したZIPを管理画面からダウンロードして、別の場所に保管しておく必要があります。
2. **新しいサーバー（または同じサーバー）に、WordPressを動かせる環境があること**
3. **データベースの中身を取り込む手段があること**（phpMyAdminなど）

### 復旧の手順

1. ZIPの中の `sbm-manifest.json` を見て、WordPressのバージョンを確認し、同じバージョンのWordPressを用意する
2. 空のデータベースを作り、ZIPの中の `database/database.sql` を取り込む
3. wp-config.php を作り、データベースの接続情報を書く（テーブル名の頭につく文字列は `sbm-manifest.json` の `table_prefix` に合わせる）
4. サーバーの `wp-content` フォルダを、ZIPの中の `wp-content` フォルダで置き換える
5. ドメインが変わる場合は、データベース内のURLを新しいドメインに置き換える（WP-CLIの `wp search-replace` を使います。テキストエディタで単純に置き換えるとデータが壊れることがあります）
6. 管理画面にログインし、「設定」→「パーマリンク」で何も変えずに「変更を保存」を押す。サイトの表示を確認する

※ 今回の制作では、管理画面から復旧する機能は作っていません（理由は「未実装事項」に書いています）。

### バックアップが正しく取れたかを確かめる方法

**プラグインが自動で行っていること**

- ZIPを作り終えたら、もう一度開き直して、壊れていないか、入っているファイルの数が合っているかを確認しています。おかしければ、そのZIPは削除してエラーを表示します
- 作成途中は仮の名前で保存し、確認が終わってから正式な名前に変えています。途中で失敗したZIPが「成功」として残ることはありません
- ZIPの「SHA-256」という値を記録して、一覧に表示しています。これはファイルの指紋のようなもので、1文字でも中身が変わると値が変わります。ダウンロードしたファイルの値と比べれば、途中で壊れたり書き換えられたりしていないかを確認できます
- 読み取れずにバックアップできなかったファイルがあれば、その数を一覧に表示します

**手動で確認する方法**

- ZIPの中の `database.sql` を別のデータベースに取り込み、元のデータと件数や中身が一致するかを比べる（今回実際に行い、一致することを確認しました）
- 新しく用意したサイトに、上の「復旧の手順」どおりにバックアップを戻し、元のサイトと同じように表示されるかを確かめる（今回実際に行い、同じサイトが表示されることを確認しました）
- 定期的に、テスト用の環境で実際に復旧してみる（いざという時に「バックアップはあったのに戻せなかった」とならないように、運用として月1回程度の実施を提案したいです）

## ④ セキュリティ対策(追加しました)

課題では必須ではありませんが、クライアントの「不正アクセスによる漏えいを防ぎたい」という要望に直接関わるので、できる範囲で対策しました。

バックアップには、ユーザー情報を含むデータベースが丸ごと入っています。バックアップが漏れることは、サイトの中身が丸ごと漏れることと同じなので、サイト本体と同じくらい慎重に扱うべきだと考えました。

- **URLから直接ダウンロードされないようにした**
  バックアップは、Webからアクセスできない場所（WordPressを置いているフォルダの1つ上の階層）に保存しています。そこに書き込めないサーバーの場合のみ、uploadsフォルダの中に保存し、その場合はアクセス禁止の設定ファイルを置き、フォルダ名とファイル名をランダムな文字列にして推測されにくくしています
- **管理者だけが操作できるようにした**
- **なりすまし操作を防いだ**
  作成・ダウンロード・削除のすべてで、本人が管理画面から操作したものかを確認しています
- **関係ないファイルをダウンロードされないようにした**
  ダウンロードはファイル名ではなく、バックアップごとに割り振ったIDで指定する方式にしました。`../../wp-config.php` のような指定で、サーバー上の他のファイルを取り出されることを防ぎます
- **エラー画面からサーバーの情報が漏れないようにした**
  予期しないエラーの詳しい内容は画面には出さず、サーバーのログにだけ記録します

**サーバーがnginxの場合の注意**

アクセス禁止の設定ファイル（.htaccess）はApacheでしか効きません。保存先がuploadsフォルダの中になり、かつnginxの場合は、管理画面に警告を表示します。その場合は、wp-config.php に次の1行を追加して、Webからアクセスできない場所を保存先に指定してください。

```php
define( 'SBM_BACKUP_DIR', '/home/example/backups' );
```

**今回できなかった対策**

- ZIPファイルの暗号化（漏れたとしても中身を読めないようにする、最も効果の大きい対策です）
- ダウンロード前のパスワード再入力
- 誰がいつダウンロードしたかの記録

## ⑤ 今後の機能拡張

### 1日1回の自動バックアップ

WordPressには、決まった時間に処理を実行する「WP-Cron」という仕組みがあります。ただしWP-Cronは「サイトに誰かがアクセスしたとき」に動くため、アクセスの少ないサイトでは予定どおりに動かないことがあります。

そのため、次の構成を考えています。

- サーバー側の定期実行機能（cron）を使って、毎日深夜など決まった時刻に確実に実行する
- サイトへのアクセスが少ない時間帯に実行する
- 失敗したときは管理者にメールで知らせる
- 「最後に成功したのが1日以上前」になったときにも知らせる（失敗の通知そのものが届かない場合にも気付けるように）

今回のプラグインは、バックアップを作る処理を1か所にまとめてあるので、それを定期的に呼び出すだけで実現できます。

### Google Drive等の外部ストレージへの保存

同じサーバーの中にバックアップを置いていると、サーバーが故障したときや乗っ取られたときに、バックアップも一緒に失われてしまいます。外部に保存するのは、それを防ぐためです。

- **Google Drive**：Googleが用意している連携の仕組み（API）を使ってアップロードします。担当者個人のアカウントではなく、会社の共有ドライブに保存すると、担当者が変わっても困りません
- **Amazon S3などのクラウドストレージ**：業務用途ではこちらをおすすめしたいです。「一定期間は削除も上書きもできない」設定ができるため、サイトが乗っ取られてもバックアップを消されません。古いファイルを自動で削除する設定もできます

運用面では、次の点に気をつけます。

- 外部サービスに接続するための鍵（パスワードのようなもの）は、データベースではなく wp-config.php に書く
- 鍵には「追加はできるが削除はできない」権限だけを与える
- アップロードする前にZIPを暗号化する
- アップロードは時間がかかるので、バックアップ作成とは別に後から実行し、失敗したら再挑戦する

### 過去30日分のバックアップ管理

- 新しいバックアップが成功したことを確認してから、30日より古いものを自動で削除する（先に古いものを消すと、新しいものが失敗したときにバックアップが無くなってしまうため）
- 残す日数を管理画面で設定できるようにする
- 30日分をサーバーの中に置くと容量が足りなくなることが多いので、「サーバーには数日分、30日分は外部ストレージに」という分担を考えています

### 大容量サイト（例：50GB）への対応

今回の「ボタンを押したらその場で全部をZIPにまとめる」方法は、50GBのサイトでは使えません。

- 処理が時間切れで止まる
- ZIPを作るために、さらに50GB近い空き容量が必要になる
- サーバーに負荷がかかり、サイトの表示が遅くなる

そこで、次のような方法を考えています。

- **少しずつ分けて処理する**：「ファイルを1,000個ずつ追加する」「データベースは表ごとに書き出す」のように処理を小分けにし、途中で止まっても続きから再開できるようにします
- **変わったところだけバックアップする**：50GBの大部分は、一度アップロードしたら変わらない画像です。前回から変更・追加されたファイルだけを保存すれば、毎回の量を大きく減らせます
- **ZIPを分割する**：数GBずつに分けて、ダウンロードやアップロードに失敗したときにやり直す量を減らします
- **そもそもの構成を見直す**：この規模になると、PHP（プラグイン）で処理するより、サーバー側のバックアップの仕組みを使う方が適しています。画像をクラウドストレージに置く構成にすれば、サーバー側のバックアップ自体を小さくできます。プラグインは「バックアップの実行を指示する」「結果を表示する」役割に絞るのがよいと考えています

## ⑥ AIツールの利用

### 使用ツール

Claude Code（Anthropic社のAIツール）

### 主な利用目的

- 課題文から、確認すべきことや設計の方針を整理する
- プラグインのコード、テスト用スクリプト、READMEの下書きを作成する
- ローカル環境（Local）でのテストの実行

### AIが提案したコードについて、確認・修正した箇所

AIが作ったプラグインを、自分で管理画面から実際に操作して、正しく動くかを確認しました。

- 「バックアップを作成」ボタンを押して、バックアップが作られ、履歴に表示されることを確認しました
- バックアップをダウンロードできることを確認しました
- エラーがきちんと表示されるかを確認するために、わざと失敗する状況を作り、次の4つのエラーが画面に表示されることを確かめました
  - サーバー上のバックアップのファイル名を変えて、「ファイルが見つかりません」と表示されること
  - バックアップを削除した後に、そのダウンロード用のURLを開いて、「指定されたバックアップは存在しません」と表示されること
  - テスト用の小さなプラグイン（mu-plugins）を一時的に置いて、バックアップする対象のフォルダが存在しない状態にし、「バックアップ対象のディレクトリが存在しません」と表示されること
  - 同じく、保存先のフォルダを作れない状態にして、「バックアップの保存先ディレクトリを作成できませんでした」と表示されること
- テストが終わった後、テスト用のプラグインは削除して元の状態に戻しました

確認の途中で、「このサーバーは nginx のため、保存先の .htaccess による直接アクセス禁止が効きません」という見慣れない警告が出ました。エラー確認のために、バックアップの保存先を一時的に変えたときです。

最初は不具合かと思いましたが、原因を調べたところ、次のことが分かりました。

- バックアップの保存先が、Webから誰でも見られる場所（公開フォルダの中）になっていた
- 今回の環境のサーバー（nginx）では、その場所へのアクセスを禁止する設定ファイルが効かない
- 「URLを知っている人にバックアップをダウンロードされるおそれがある」と知らせる警告だった

つまり、不具合ではなく、危ない状態になったことを正しく知らせてくれる、意図どおりの動作でした。保存先を元に戻すと、警告が消えることも確認しました。

### AIの回答を採用しなかった例

- AIが最初に作成したREADMEは、目次のリンクや専門用語が多く、表に詰め込んだ書き方になっていました。読む人にとって分かりにくいと感じたため、専門用語に説明を加え、自分の言葉に近い書き方に直しました
- スクリーンショットの一覧をREADMEに載せる案がありましたが、スクリーンショットは別に提出するため、READMEには載せないことにしました

## 動作確認・テスト結果

テスト日：2026年11月9日
環境：Local（WordPress 7.1.4、PHP 8.2.29、MySQL 8.4.0、nginx）

## 未実装事項と今後の改善方針

**管理画面からの復旧機能**
復旧はデータベースとファイルを上書きする操作で、途中で失敗するとサイトが表示されなくなる危険があります。限られた時間で安全に作るのは難しいと判断し、今回は手順書（③）での対応としました。作る場合は、「復旧前に自動でバックアップを取る」「作業中はメンテナンス画面を表示する」「失敗したら元に戻す」をセットで作る必要があると考えています。

**復旧したサイトが、元のサイトのバックアップ保存先を見てしまう問題**
バックアップの保存先の場所はデータベースに記録しているため、復旧するとその記録も一緒に戻ります。今回のように同じサーバーの中で別のサイトとして復旧すると、復旧したサイトの管理画面に元のサイトのバックアップが表示され、そこから削除もできてしまいます。別のサーバーに復旧した場合は、記録された場所が存在しないため新しい保存先が作られますが、古い履歴は「ファイルが見つかりません」と表示されます。
「保存先」や「履歴」をバックアップに含めるかどうかは、同じ場所に戻す場合（含めた方が便利）と、別の場所に戻す場合（含めない方が安全）で正解が変わります。今後は、サイトのURLが変わったことを検知して、保存先と履歴を新しく作り直す仕組みを考えています。

**大きなサイトへの対応**
今回はボタンを押したらその場で全部を処理するため、大きなサイトでは時間切れになる可能性があります。⑤に書いた「少しずつ分けて処理する」方法に変える予定です。

**自動バックアップ・外部ストレージ・30日分の管理**
必須範囲外のため未実装です。方針は⑤に書いたとおりです。

**バックアップの暗号化**
暗号化の鍵をどこに保管するか、鍵を無くしたらどうするか、をクライアントと決める必要があるため、今回は見送りました。

**バックアップ中のデータの整合性**
バックアップを作っている最中に注文や投稿があると、ファイルとデータベースの内容が少しずれる可能性があります。データベースの機能を使って「ある瞬間の状態」をまとめて読み出す方法で改善できますが、検証の時間が取れませんでした。

**作成中の進み具合の表示**
今はボタンを押した後、終わるまで待つだけです。分割処理に変えるときに、あわせて進み具合を表示できるようにしたいです。

**自動チェックの仕組み**
コーディング規約の自動チェック（PHPCS）や、より本格的なテスト（PHPUnit）は導入できていません。今後、GitHubに変更を上げたときに自動で実行されるようにしたいです。
